# Архитектура

## Текущая архитектура

```
Интерфейс (React, Vite, ECharts)         localhost:3000
  чат, графики, дашборды, данные, экспорт Excel / PNG / PDF
        │  HTTP JSON /api/...
        ▼
API (FastAPI)                            localhost:8000
  чат и фоновые задачи, дашборды, запросы, источники, CSV, каталог, KPI
        │
        ▼
LLM-агент (backend/llm)  ──────────────▶  Открытая LLM, OpenAI-совместимый API
  выбор таблицы, SQL, проверки, расчёты     Ollama / vLLM, по умолчанию qwen2.5:3b
        │
        ▼
PostgreSQL 16
  схема raw: сырые CSV, все поля TEXT; роль bi_reader только для чтения
  + внешние PostgreSQL (только чтение)
```

### Путь вопроса

1. Пользователь задаёт вопрос в чате. Интерфейс создаёт фоновую задачу
   (`POST /api/chat/jobs`) и показывает этапы выполнения.
2. Агент выбирает таблицу кодом, а не моделью: слова вопроса сравниваются с названиями
   таблиц, колонок и значениями категорий. Ничья — уточняющий вопрос с вариантами,
   нет совпадений — вежливый отказ.
3. Строится временная таблица `t`: безопасное приведение текстовых полей к числам и датам
   по каталогу данных (десятичная запятая, даты, пустые значения).
4. Модель пишет один `SELECT` к `t`. Модели показываются названия и типы колонок
   и реальные значения категорий, но не строки данных.
5. SQL проверяется до выполнения:
   - `sql_guard.py`: один `SELECT`, без DDL/DML и опасных функций, только таблица `t`;
   - `semantics.py`: смысл запроса совпадает с вопросом («сколько» → COUNT/SUM,
     фильтры только из вопроса).
   Ошибку модель получает обратно и исправляет запрос, до 3 попыток.
6. Запрос выполняется под ролью `bi_reader` в транзакции только для чтения:
   таймаут 20 с, не больше 200 строк.
7. Цифры, изменения, лидеров и выводы считает код. Модель только пересказывает
   готовый результат простым языком.
8. Ответ: текст, таблица, спецификация графика, SQL и этапы. Тип графика выбирается
   по форме результата: время → линия, доли → круговая, категории → столбцы.

### Данные и каталог

- CSV загружаются как есть: все поля `TEXT`, исходные заголовки и файлы сохраняются
  в `bi_meta.imports`. Преобразования делаются внутри платформы.
- Каталог (`db/`) строится автоматически по любой базе: профиль колонок, аудит типов,
  описание таблиц, связи между таблицами, бизнес-словарь и KPI.
- Новая таблица из CSV или внешняя PostgreSQL каталогизируются сразу после подключения.

### Хранение

| Что | Где |
|---|---|
| Данные | PostgreSQL, схема `raw` |
| Дашборды, сохранённые запросы | `data/dashboards.json`, `data/saved_queries.json` (атомарная запись) |
| Внешние источники | `data/datasources.json`, пароли зашифрованы (Fernet) |
| Контекст диалога | память backend по `session_id` |
| Список диалогов | браузер пользователя (localStorage) |

### Безопасность

- Агент работает только под ролью `bi_reader`, у неё нет прав на запись.
- Проверка SQL до выполнения, read-only транзакция, таймаут, лимит строк.
- Модель не видит строки данных, только описание колонок и значения категорий.
- Пароли внешних баз зашифрованы и не возвращаются в интерфейс; адреса проверяются
  на SSRF (запрещены link-local, metadata, multicast).
- Нет обращений к внешним сервисам: модель, база и интерфейс работают локально.

### Стек

| Слой | Технологии | Почему |
|---|---|---|
| Интерфейс | React 18, Vite 5, Apache ECharts 5, jsPDF, fflate | быстрая сборка, графики любого типа без лицензий, экспорт без сервера |
| API | Python 3.12, FastAPI, Pydantic | асинхронный API, схема ответа проверяется автоматически |
| Агент | собственный код без фреймворков, OpenAI-совместимый клиент | полный контроль проверок, любая открытая модель |
| Модель | qwen2.5:3b через Ollama (`backend/llm/Modelfile`) | работает на обычном ноутбуке; заменяется настройкой `LLM_MODEL` |
| База | PostgreSQL 16, psycopg 3 | требование кейса, read-only роли и таймауты из коробки |
| Тесты | pytest, unittest, контрольные расчёты, оценка точности агента | CI на каждый pull request |

### Почему так

- **Слабая модель не должна считать.** Модель до 80B может ошибиться в арифметике
  и придумать цифры. Поэтому таблицу выбирает код, SQL проверяется дважды, а все числа
  в ответе берутся из результата запроса.
- **Сырые данные остаются сырыми.** Кейс запрещает предобработку: CSV хранятся как
  текст, типы определяет каталог, приведение делается в запросе (`t`).
- **Неизвестная база.** Ничего не зашито под 9 таблиц кейса: каталог, связи и
  значения категорий строятся автоматически для любой PostgreSQL.

## Идеальная архитектура

Что бы мы сделали при большем сроке и нагрузке:

| Направление | Сейчас | Цель |
|---|---|---|
| Модель | одна модель 3B | маршрутизация: малая модель для выбора таблицы и уточнений, крупная (30–70B, vLLM) для SQL и выводов |
| Поиск по каталогу | совпадение слов | векторный поиск по описаниям колонок и примерам вопросов (pgvector) |
| Хранение состояния | JSON-файлы, память процесса | PostgreSQL для дашбордов, запросов и контекста; Redis для очереди задач |
| Тяжёлые запросы | на исходных таблицах | материализованные представления с приведёнными типами, ClickHouse для больших объёмов |
| Источники | PostgreSQL, CSV | ClickHouse, MySQL, Excel, Parquet через единый слой коннекторов |
| Доступ | без входа | вход через SSO, роли, построчные политики доступа (RLS) |
| Развёртывание | процессы вручную | Docker Compose со всеми сервисами, Kubernetes для нескольких команд |
| Наблюдаемость | логи | метрики точности и задержки по каждому вопросу, трассировка запросов агента |
| Качество | 68 вопросов с эталоном | регулярный прогон набора и сравнение моделей при каждом изменении |
