# BI-06: воспроизводимые эталонные аналитические проверки

Задача #34: отличать ошибку данных от ошибки LLM.

- \`db/golden_checks.json\` содержит 25 **детерминированных SQL-проверок** для девяти исходных CSV в схеме \`raw\`.
- Проверяются количества строк, продажи/возвраты, три канала продаж,
  разбиения по категориям и согласованность агрегатов.
- Никаких выдуманных оценок: **61 138 уникальных заказов без карты** и
  **122 805 строк без карты** пока оставлены для отдельного утверждения
  точных имён колонок/значений фильтра, а не как непроверенный SQL.
- Эти тесты **не проверяют понимание естественного языка моделью**. Для
  оценки LLM нужно пропускать аналогичные вопросы через \`/api/chat\` и
  сравнивать полученный SQL/результат с эталоном. Не считать простой
  текстовый ответ достаточным доказательством точности.

## Запуск на компьютере с загруженной базой

Из корня репозитория:

\`\`\`bash
source .venv/bin/activate
# Подключение bi_reader настраивается локально в .env.
# Используйте отдельный пароль от bi_user и не коммитьте его.
python db/run_golden_checks.py --report data/golden-report.json
\`\`\`

Необходимые ключи \`.env\`: \`POSTGRES_HOST\`, \`POSTGRES_PORT\`,
\`POSTGRES_DB\`, \`POSTGRES_READER_USER=bi_reader\`,
\`POSTGRES_READER_PASSWORD\`. Нужны исходные таблицы организаторов в
\`raw\`, загруженные **без изменения** по \`db/README.md\`.

Раннер выполняет каждый запрос в \`READ ONLY\` транзакции с таймаутом.
При несовпадении/ошибке возвращает ненулевой код, а в отчёте видны
ожидаемый и фактический результаты. Не запускайте от \`bi_user\`.

## Unit tests без PostgreSQL

\`\`\`bash
python -m unittest discover -s db -p 'test_*.py'
\`\`\`

Обычный GitHub CI проверяет формат набора и логику раннера, **не**
прогоняет 25 SQL по настоящим данным. Участнику с готовой локальной БД
необходимо запустить команду выше, после чего отдельно протестировать
LLM по соответствующим вопросам. Контрольные количества относятся
только к исходному датасету; для вновь загруженных CSV нужен отдельный
набор эталонов.
