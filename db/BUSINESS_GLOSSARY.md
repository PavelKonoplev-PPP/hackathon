# BI-37 — бизнес-словарь данных

Словарь создаётся из `data/schema-catalog.json` и предлагает понятные описания полей. Предложения **не равны проверенным определениям**.

Запуск из корня репозитория:

```bash
python db/business_glossary.py build
python db/business_glossary.py approve \
  --table data_01_Продажи \
  --column "Канал продажи" \
  --description "Канал, через который зарегистрирована операция продажи." \
  --synonym "канал продаж"
python db/business_glossary.py build
```

Файлы в игнорируемой Git папке `data/`:
- `business-glossary.json`: итоговый контракт с `status` (`proposed`, `approved`, `needs_review`), описанием, синонимами и единицами измерения.
- `business-glossary-overrides.json`: отдельные ручные определения, переживающие повторную генерацию.

Если технический тип поля меняется, старое подтверждение переводится в `needs_review`. При удалении поля оно не попадает в итоговый словарь, но остаётся в overrides на случай восстановления. Автоматические названия основаны только на названии поля и его техническом типе, они не подтверждают бизнес-формулы, JOIN или единицы, которых нет в названии.

Интеграция с backend: после обновления технического каталога (BI-10) запустить `update_glossary(catalog_path, overrides_path, output_path)`; для редактора предоставить контролируемое действие `approve`, не разрешая клиенту записывать произвольные файлы. Для LLM: использовать как доверенные определения только записи со статусом `approved`, остальные — как подсказки с явным предупреждением. Не выдавать словарь за подтверждение данных/метрик.

Примечание: CLI не создает UI для редактирования и сам по себе не подключает словарь к FastAPI/LLM. Для полной реализации BI-37 эти компоненты остаются интеграционными задачами.

Проверка: `python -m unittest discover -s db -p 'test_*.py'`.
