# Полные временные границы в каталоге

После проверки колонок с типом \`date\` или \`timestamp\` аудит сохраняет фактические \`MIN/MAX\` только по корректно преобразованным значениям. Для этого используется тот же SELECT, что считает пропуски и ошибки типов, поэтому дополнительного полного прохода по таблице не требуется.

В отчёте аудита для даты появится:

\`\`\`json
"date_range": {
  "min": "2025-02-01",
  "max": "2025-03-31",
  "scope": "full_column_valid_values"
}
\`\`\`

Каталог хранит диапазон в \`column.conversion.date_range\`. Счётчики \`missing_rows\`, \`invalid_rows\`, \`convertible_rows\` остаются отдельно в \`conversion.quality\`. При отсутствии корректных дат границы равны \`null\`.

В описании данных отображается диапазон **по каждому проверенному полю даты**. Нельзя без уточнения объединять дату создания, закрытия, доставки и других событий в один «период всей базы». Когда метаданные старого формата не содержат диапазона, отображается «точный период пока не проверен», а не предполагаемые даты.

## Проверка

\`\`\`bash
python -m unittest discover -s db -p 'test_*.py'
python -m unittest discover -s backend -p 'test_*.py' -t .
\`\`\`

Для реальной базы: после загрузки CSV обновить каталог штатным \`refresh_catalog\`, проверить \`data/schema-catalog.json\` и задать «Опиши данные» на \`VITE_MOCK=0\`. При сравнении сверить \`MIN/MAX\` и счётчики с отдельным read-only SQL. Сырые CSV и таблицы не изменяются.

**Ограничение:** поля, которые профилировщик не признал датами или которые ещё не прошли полный аудит, не получают точных границ автоматически. Обновление кэша происходит штатным механизмом профилирования, не при каждом сообщении в чат.
