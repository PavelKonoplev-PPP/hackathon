# PostgreSQL — база данных хакатона

Используем **PostgreSQL 16** вместо ClickHouse. Датасеты организаторов загружаем
в отдельную схему `raw`. Это тестовая БД, а не заранее зашитая схема приложения.

## Быстрый запуск

Из корня репозитория:

```bash
cp .env.example .env
# В .env замените POSTGRES_PASSWORD на свой локальный пароль
docker compose up -d postgres
docker compose ps

./scripts/fetch_data.sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r db/requirements.txt
python db/load_csv.py
python db/inspect_db.py
```

`load_csv.py` рекурсивно находит CSV в папке `Исходники/`; можно указать
другую папку флагом `--directory`. Повторный импорт той же таблицы по
умолчанию запрещён. Опция `--replace` **удаляет и пересоздаёт** ранее
импортированные таблицы — не используйте без необходимости.

## Как храним данные

- Оригинальные CSV не меняем и не коммитим.
- Все значения при загрузке записываются в `TEXT`: десятичная запятая,
  даты, идентификаторы с ведущими нулями остаются в исходном виде.
- Имена колонок берутся из заголовка; пустые и повторяющиеся уточняются.
  Длинные идентификаторы укорачиваются до лимита PostgreSQL (63 байта).
- Имена таблиц формируются из имени CSV с префиксом `data_`,
  например `01_Продажи.csv` → `raw."data_01_Продажи"`.
- Соответствие исходных заголовков и имён колонок хранится в
  `bi_meta.imports`.
- Числовые, временные и иные преобразования выполняются **внутри**
  платформы после загрузки. Агент не должен считать значения в TEXT
  числовыми без проверки/преобразования.

Пример SQL для исследователя структуры:

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'raw' AND table_type = 'BASE TABLE';

SELECT column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'raw'
  AND table_name = 'data_01_Продажи'
ORDER BY ordinal_position;
```

## Подключение backend

Параметры берутся из корневого `.env`: `POSTGRES_HOST`, `POSTGRES_PORT`,
`POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_SCHEMA`.

- Если backend работает на хосте, `POSTGRES_HOST=127.0.0.1`.
- Если backend позднее запустят в том же Docker Compose,
  используйте `POSTGRES_HOST=postgres` и порт `5432`.
- SQL-агент должен проверять схему `raw`, а не предполагать имена таблиц,
  и использовать диалект PostgreSQL. Можно явно указывать схему в SQL
  или установить `search_path=raw,public` при подключении.

**Безопасность:** пользовательский SQL нельзя выполнять с правами владельца
БД. Для агента потребуется отдельный пользователь только для чтения
(`GRANT USAGE ON SCHEMA raw` и `GRANT SELECT ON ALL TABLES IN SCHEMA raw`),
таймаут запросов и блокировка DDL/DML на уровне приложения.
Скрипт импорта использует учётную запись владельца только для настройки
локальных тестовых таблиц.

## Отдельный пользователь для backend / LLM (только чтение)

После загрузки CSV настройте роль `bi_reader`. В корне проекта:

```bash
# Выполняет db/setup_readonly.sql внутри контейнера, без копирования файлов в контейнер
docker compose exec -T postgres psql -U bi_user -d hackathon -v ON_ERROR_STOP=1 < db/setup_readonly.sql

# Устанавливаем пароль интерактивно, чтобы не оставлять его в shell history
docker compose exec postgres psql -U bi_user -d hackathon
```

В интерактивной консоли `psql` выполните `\password bi_reader`, дважды
введите **новый** пароль (он не отобразится), затем `\q`.
Не присылайте пароль в чат и не сохраняйте его в Git.

Проверьте соединение **именно по TCP с проверкой пароля**:

```bash
docker compose exec postgres psql -h 127.0.0.1 -U bi_reader -d hackathon -W
```

Войдя как `bi_reader`, проверьте:

```sql
SHOW transaction_read_only;
SELECT count(*) FROM raw."data_01_Продажи";
SELECT
    has_table_privilege(current_user, 'raw."data_01_Продажи"', 'SELECT') AS can_select,
    has_table_privilege(current_user, 'raw."data_01_Продажи"', 'INSERT') AS can_insert,
    has_table_privilege(current_user, 'raw."data_01_Продажи"', 'UPDATE') AS can_update,
    has_table_privilege(current_user, 'raw."data_01_Продажи"', 'DELETE') AS can_delete;
```

Ожидаем `on`, `500000` и соответственно `true/false/false/false`.
Для выхода используйте `\q`. Тесты не изменяют данные.

**Контракт для backend:** приложение использует `bi_reader` вместо владельца
`bi_user`, параметры подключения должны храниться в **локальном** `.env`
или другом менеджере секретов. Для контейнера backend в той же Docker Compose
сети хост — `postgres`, порт — `5432`; для запуска на Mac хост —
`127.0.0.1`. Локальная PostgreSQL не открыта во внешнюю сеть.

Скрипт даёт `SELECT` на текущие таблицы `raw` и
`bi_meta.imports`, а также на новые таблицы `raw`, созданные тем же
владельцем импортёра (`bi_user`). Если CSV будут импортироваться от другого
владельца, будущие права нужно настроить отдельно.

**Ограничения безопасности:** настройка роли защищает исходные таблицы от
изменений, но не заменяет проверку сгенерированного SQL. Backend всё равно
должен запускать проверенные запросы в явно read-only транзакциях, ограничивать
время/число строк и блокировать DDL, DML и потенциально опасные функции.
`default_transaction_read_only` и `statement_timeout` — значения по
умолчанию, а не абсолютные запреты для любого возможного SQL. Привилегия
`TEMP` на базу в PostgreSQL может быть у `PUBLIC`: доступ только для чтения
относится к **постоянным исходным таблицам**, а не означает полного отсутствия
операций с временными объектами.

## Границы этой задачи

`load_csv.py` — **утилита команды для заполнения тестовой БД**.
По ТЗ самой платформе также понадобится реализовать загрузку произвольного
CSV и внутреннюю обработку неизвестных данных. Эта функция остаётся задачей
backend и **не считается реализованной** данным скриптом.

## Автоматическое профилирование неизвестных таблиц

Скрипт `db/profile_db.py` **не меняет данные**. Он получает из
`information_schema` доступные таблицы/колонки, читает максимум 200
строк на таблицу по умолчанию из случайных блоков PostgreSQL и определяет вероятный тип колонки:
`integer`, `decimal` (включая десятичную запятую), `date`,
`timestamp`, `boolean`, `identifier`, `category`, `text`,
`mixed` или `unknown`.

Выдаёт JSON: имя таблицы, тип PostgreSQL, предполагаемый тип, уверенность,
количество пустых значений и уникальных значений **в выборке**,
примеры, минимумы/максимумы и предупреждения. Это входные метаданные для
будущего backend/LLM, а не окончательная схема для жёсткого CAST.

Пример: исследовать всё в `raw`, не выводя содержимое строк в терминал:

```bash
python db/profile_db.py --schema raw --no-examples --output data/schema-profile.json
```

Только продажи, со значениями-примерами:

```bash
python db/profile_db.py --schema raw --table data_01_Продажи --sample-size 300 --output data/sales-profile.json
```

`data/` исключена из Git. Профиль с примерами может содержать
чувствительные значения; **не коммитьте** созданный JSON.

Ограничения: на больших таблицах выборка создаётся через TABLESAMPLE SYSTEM
по случайным физическим блокам, затем строки перемешиваются. Такая выборка
быстрее полного сканирования, но не гарантирует идеальную случайность.
Редкие значения, пропуски и аномалии могут остаться незамеченными; доля пустых,
уникальность и минимумы/максимумы относятся **только к выборке**.
`estimated_total_rows` основан на статистике PostgreSQL `pg_class`,
может быть `null` или неточным до `ANALYZE`. Никакие типы исходных
колонок не меняются. Для production агенту дополнительно потребуются
контролируемые преобразования типов, проверка SQL, ролевой доступ только
для чтения, а также репрезентативное профилирование.

Прогон тестов (без подключения к PostgreSQL):

```bash
python -m unittest discover -s db -p 'test_*.py'
```

Если непустых значений не нашлось, inferred_type остаётся unknown; по
названию колонки может выдаваться отдельное поле type_hint без уверенности.
Свойства sample_method и tablesample_percent отражают способ отбора
строк, а не долю непустых значений.

## Безопасное приведение TEXT к числам и датам (PostgreSQL 16)

Модуль db/safe_cast.py генерирует безопасные SQL-выражения для SELECT
и проверяет качество столбца на всей таблице, ничего не меняя.
Поддерживает integer (bigint), decimal (numeric, точка/запятая),
date (ISO и ДД.ММ.ГГГГ), timestamp (ISO без timezone).
Пробелы и пустые значения превращаются в NULL. Значения с неверным
форматом или несуществующей датой тоже становятся NULL, а число таких
значений показывается отдельно как invalid_rows.

Для защиты CAST сначала проверяются регулярное выражение и функция
PostgreSQL 16 pg_input_is_valid. Режимы identifier, category, text,
mixed, unknown намеренно запрещены — нельзя незаметно преобразовать
код с ведущими нулями или непроверенные данные в число.

Проверка всей колонки продаж (выполняется read-only запрос):
```bash
python db/safe_cast.py --table data_01_Продажи \
  --column "Цена до скидки за единицу, руб." --kind decimal

python db/safe_cast.py --table data_01_Продажи \
  --column "Количество, шт." --kind integer
```

Для backend из db/safe_cast.py доступны:
- safe_cast_expression(column, kind): объект psycopg.sql.Composable для
  безопасной вставки в SQL SELECT;
- quality_query(schema, table, column, kind): подсчёт total_rows,
  missing_rows, invalid_rows, convertible_rows;
- audit_column(conn, schema, table, column, kind): словарь с итогами.

Тип kind должен быть проверен backend по данным профилировщика и
подтверждён при необходимости. Качество **не определяется по выборке**:
для подсчёта полного числа ошибок audit_column сканирует весь столбец,
что может занять время на больших таблицах. Пропуск некорректных
значений через NULL может исказить SUM/AVG: перед аналитикой смотрите
на invalid_rows и предупреждайте пользователя о неполных данных.

Не поддерживаются валютные символы, разделители тысяч, экспоненциальная
запись, нестандартные даты и timestamp с часовыми поясами. Такие случаи
требуют отдельной проверенной стратегии. Профилировщик и SQL-валидатор
остаются независимыми компонентами; это не функция выполнения SQL от LLM.

## Аудит типов по всем датасетам

После создания JSON профиля можно проверить **все** колонки с типами
`integer`, `decimal`, `date`, `timestamp` на полном объёме данных:

```bash
# Проверка одной таблицы перед полным запуском
python db/audit_profile.py --table data_02_Техническая_поддержка --output data/support-audit.json

# Затем все таблицы и все подходящие колонки (может выполняться заметное время)
python db/audit_profile.py --output data/type-audit.json
```

По умолчанию модуль читает `data/all-profile.json` (подготовить с помощью
`python db/profile_db.py --schema raw --sample-size 300 --no-examples --output data/all-profile.json`).
Для небольшой пробной проверки используйте `--limit 3`.

Модуль **не меняет данные**: результаты содержат `total_rows`,
`missing_rows`, `invalid_rows`, `convertible_rows` для каждой колонки
и общую статистику. Коды, категории, `mixed` и `unknown` не приводятся.
Каждая колонка проверяется запросом к полной таблице, что может быть затратным
по времени; запросы выполняются с ограничением времени, неудачи фиксируются
как `status=error`, остальные проверки продолжаются. Пропуски сами по себе
не являются ошибкой типа: например, дата закрытия обращения может быть пустой.
Если `invalid_rows > 0`, перед SUM/AVG и другими расчётами нужно учитывать
неполное покрытие данных. JSON-результаты находятся в `data/` (gitignored).

## Единый каталог метаданных для backend

После создания `data/all-profile.json` и `data/type-audit.json`
объедините их в один машиночитаемый файл:

```bash
python db/catalog_db.py --profile data/all-profile.json --audit data/type-audit.json --output data/schema-catalog.json
```

В backend можно использовать `build_catalog(profile, audit)` из
`db/catalog_db.py`. Каталог включает исходные типы PostgreSQL,
предполагаемые типы и статистику из выборки, а также результаты полного
аудита. Для числовых/временных полей добавляется политика:
`safe_complete` (всё заполнено и приводится),
`safe_with_nulls` (пропуски, остальные значения корректны),
`blocked_invalid` (есть ошибки формата),
`unverified` (полный аудит отсутствует или нет непустых значений).
Для текстовых полей, категорий и идентификаторов используется
`not_applicable`.

Примеры значений по умолчанию в каталог не попадают; флаг
`--include-examples` включайте только если это разрешено для данных.
Каталог не подтверждает межтабличные связи (`relationships_verified=false`).
`confidence` из профиля — эвристика, не гарантия корректного приведения.
Каталог требует, чтобы аудит относился к тому же профилю; после обновления
данных нужен новый профиль и новый аудит.

## Автоматический поиск кандидатов на связи между таблицами

Из готового каталога можно искать совместимые идентификаторы по совпадению
**полного** значения, не вырезая префиксы и не подменяя бизнес-семантику:

```bash
python db/discover_relationships.py --catalog data/schema-catalog.json --output data/relationships.json
```

Скрипт сначала смотрит до 1000 непустых значений каждого поля через
`TABLESAMPLE SYSTEM` и определяет доминирующий префикс вида `ПР-КЛ-`.
Идентификаторы с разными префиксами не соединяются, числовые суффиксы
не приравниваются. Для совпадающих префиксов проверяет на всей таблице
существование ссылок и уникальность целевого ключа. Это **техническая**
проверка, не бизнес-подтверждение: в отчёте все кандидаты имеют
`business_semantics_approved=false` и `can_auto_join=false`.
Два поля одной таблицы с подходящими именами (`исходн`, `предыдущ`
и др.) проверяются как гипотезы самоссылки.

Выходной JSON содержит `identifiers`, `relationships` и `summary`;
не содержит исходных полных ID или личных данных. Есть ограничения
`--sample-size` (10..1000), `--max-pairs` (по умолчанию 20).
Обнаружение потенциальных пар **не исчерпывающее**: редкие или
нестандартные форматы ID могут быть пропущены выборкой. Для
неизвестных бизнес-связей по разным форматам ID нужна таблица
соответствий и ручное подтверждение. Роль БД только для чтения.
Повторный импорт данных требует нового каталога и новой проверки связей.

## Аудит идентификаторов без устойчивого префикса

После создания `data/relationships.json` проверьте оставшиеся ID
на **всём объёме** таблиц, а не только по выборке:

```bash
python db/audit_identifiers.py --relationships data/relationships.json --output data/unprefixed-id-audit.json
```

Скрипт читает только поля, у которых в отчёте `dominant_prefix=null`.
Для каждого поля считает `total_rows`, `missing_rows`, `distinct_keys`,
`duplicate_rows`, `repeating_keys`, `rows_in_repeating_keys`,
`max_rows_per_key`, `numeric_only_keys`; сами значения не выдаёт.
`can_group_by=true` означает только наличие ключей для группировки в
пределах одной таблицы, но **не** разрешает `JOIN` с другой таблицей.
Все `can_auto_join=false` до явной проверки бизнес-семантики.
Полный аудит читает всю таблицу и может потребовать времени.

## Итоговый каталог связей и группировок для backend

Когда готовы `data/relationships.json` и `data/unprefixed-id-audit.json`,
соберите единый контракт:

```bash
python db/relationship_catalog.py \
  --relationships data/relationships.json \
  --id-audit data/unprefixed-id-audit.json \
  --group "data_08_Фоновые_задания:Код цепочки запусков" \
  --output data/relationship-catalog.json
```

Параметр `--group` необязателен и допускает повторение для других
полей-идентификаторов. Для указанного поля утилита запускает полный
read-only аудит (количество уникальных групп, повторов, пропусков, максимальный
размер группы) и добавляет его к шести непрефиксным полям из аудита.
Это позволяет описать цепочки фоновых заданий как `GROUP BY`, а не `JOIN`.

Контракт `data/relationship-catalog.json` содержит:
- `join_candidates` с `technical_reference_verified`,
  `policy=manual_approval_required` и `can_auto_join=false`.
  Совпавший ключ **не равен** подтверждённой бизнес-связи.
- `grouping_fields` с полными количествами ключей, пропусков, повторов
  и `missing_fraction`. `can_group_by=true` не разрешает `JOIN`.
- `rules` с обязательной проверкой бизнес-смысла, запретом удаления
  префиксов идентификаторов и предупреждением о пропусках.

При изменении исходных данных перепроверьте каталог. Backend должен
использовать явно разрешённые пользователем/разработчиком отношения,
а не все найденные кандидаты. Для анализа независимых таблиц корректнее
строить отдельные запросы, чем придумывать соединение.
