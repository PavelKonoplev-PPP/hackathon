# PostgreSQL — база данных хакатона

Используем **PostgreSQL 16** вместо ClickHouse. Датасеты организаторов загружаем
в отдельную схему `raw`. Это тестовая БД, а не заранее зашитая схема приложения.

## Быстрый запуск

Из корня репозитория:

```bash
cp .env.example .env
# В .env замените POSTGRES_PASSWORD на свой локальный пароль
docker compose up -d postgres
docker compose ps

./scripts/fetch_data.sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r db/requirements.txt
python db/load_csv.py
python db/inspect_db.py
```

`load_csv.py` рекурсивно находит CSV в папке `Исходники/`; можно указать
другую папку флагом `--directory`. Повторный импорт той же таблицы по
умолчанию запрещён. Опция `--replace` **удаляет и пересоздаёт** ранее
импортированные таблицы — не используйте без необходимости.

## Как храним данные

- Оригинальные CSV не меняем и не коммитим.
- Все значения при загрузке записываются в `TEXT`: десятичная запятая,
  даты, идентификаторы с ведущими нулями остаются в исходном виде.
- Имена колонок берутся из заголовка; пустые и повторяющиеся уточняются.
  Длинные идентификаторы укорачиваются до лимита PostgreSQL (63 байта).
- Имена таблиц формируются из имени CSV с префиксом `data_`,
  например `01_Продажи.csv` → `raw."data_01_Продажи"`.
- Соответствие исходных заголовков и имён колонок хранится в
  `bi_meta.imports`.
- Числовые, временные и иные преобразования выполняются **внутри**
  платформы после загрузки. Агент не должен считать значения в TEXT
  числовыми без проверки/преобразования.

Пример SQL для исследователя структуры:

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'raw' AND table_type = 'BASE TABLE';

SELECT column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'raw'
  AND table_name = 'data_01_Продажи'
ORDER BY ordinal_position;
```

## Подключение backend

Параметры берутся из корневого `.env`: `POSTGRES_HOST`, `POSTGRES_PORT`,
`POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_SCHEMA`.

- Если backend работает на хосте, `POSTGRES_HOST=127.0.0.1`.
- Если backend позднее запустят в том же Docker Compose,
  используйте `POSTGRES_HOST=postgres` и порт `5432`.
- SQL-агент должен проверять схему `raw`, а не предполагать имена таблиц,
  и использовать диалект PostgreSQL. Можно явно указывать схему в SQL
  или установить `search_path=raw,public` при подключении.

**Безопасность:** пользовательский SQL нельзя выполнять с правами владельца
БД. Для агента потребуется отдельный пользователь только для чтения
(`GRANT USAGE ON SCHEMA raw` и `GRANT SELECT ON ALL TABLES IN SCHEMA raw`),
таймаут запросов и блокировка DDL/DML на уровне приложения.
Скрипт импорта использует учётную запись владельца только для настройки
локальных тестовых таблиц.

## Границы этой задачи

`load_csv.py` — **утилита команды для заполнения тестовой БД**.
По ТЗ самой платформе также понадобится реализовать загрузку произвольного
CSV и внутреннюю обработку неизвестных данных. Эта функция остаётся задачей
backend и **не считается реализованной** данным скриптом.

## Автоматическое профилирование неизвестных таблиц

Скрипт `db/profile_db.py` **не меняет данные**. Он получает из
`information_schema` доступные таблицы/колонки, читает максимум 200
первых строк на таблицу по умолчанию и определяет вероятный тип колонки:
`integer`, `decimal` (включая десятичную запятую), `date`,
`timestamp`, `boolean`, `identifier`, `category`, `text`,
`mixed` или `unknown`.

Выдаёт JSON: имя таблицы, тип PostgreSQL, предполагаемый тип, уверенность,
количество пустых значений и уникальных значений **в выборке**,
примеры, минимумы/максимумы и предупреждения. Это входные метаданные для
будущего backend/LLM, а не окончательная схема для жёсткого CAST.

Пример: исследовать всё в `raw`, не выводя содержимое строк в терминал:

```bash
python db/profile_db.py --schema raw --no-examples --output data/schema-profile.json
```

Только продажи, со значениями-примерами:

```bash
python db/profile_db.py --schema raw --table data_01_Продажи --sample-size 300 --output data/sales-profile.json
```

`data/` исключена из Git. Профиль с примерами может содержать
чувствительные значения; **не коммитьте** созданный JSON.

Ограничения: выборка — первые N строк, поэтому редкие значения, пропуски
и аномалии в других строках могут остаться незамеченными; доля пустых,
уникальность и минимумы/максимумы относятся **только к выборке**.
`estimated_total_rows` основан на статистике PostgreSQL `pg_class`,
может быть `null` или неточным до `ANALYZE`. Никакие типы исходных
колонок не меняются. Для production агенту дополнительно потребуются
контролируемые преобразования типов, проверка SQL, ролевой доступ только
для чтения, а также репрезентативное профилирование.

Прогон тестов (без подключения к PostgreSQL):

```bash
python -m unittest discover -s db -p 'test_*.py'
```
