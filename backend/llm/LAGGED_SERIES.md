# Лаговые корреляции временных рядов

Модуль \`backend/llm/lagged_series.py\` рассчитывает корреляцию Пирсона на нескольких календарных сдвигах, не изменяя исходные данные. Он работает с **готовыми агрегированными рядами** (одна строка на месяц или день) и не строит SQL самостоятельно.

## Определение лага

Сопоставляются \`X(t)\` и \`Y(t + L)\`:

- \`L > 0\` — показатель X опережает Y на L календарных периодов.
- \`L < 0\` — показатель Y опережает X на |L| периодов.
- \`L = 0\` — сопоставляются значения за один период.

Для каждого сдвига возвращаются коэффициент \`r\`, число реально сопоставленных пар \`pairs\`, и \`status\`. Календарная ось важнее позиции строки: например, между февралем и апрелем два месяца, даже если март отсутствует в исходном наборе.

## Входные данные

Файл JSON с массивом \`[period, X, Y]\`:

\`\`\`json
[
  ["2025-01", 120, null],
  ["2025-02", 180, 140],
  ["2025-03", 130, 210],
  ["2025-04", 200, 160],
  ["2025-05", 160, 230]
]
\`\`\`

Пример запуска с готовым JSON:

\`\`\`bash
python -m backend.llm.lagged_series \
  --input data/lag-series.json --grain month \
  --max-lag 3 --min-pairs 4 \
  --x-label "Реклама" --y-label "Продажи"
\`\`\`

Данные должны быть предварительно агрегированы на одной временной шкале с совместимыми границами периодов. Дубликаты периодов отклоняются: усреднять или суммировать их без бизнес-правила нельзя.

## Статусы и ограничения

- \`checked\` — есть достаточное число пар и ненулевая дисперсия обоих рядов.
- \`insufficient_pairs\` — количество сопоставленных значений меньше \`min_pairs\`.
- \`zero_variance\` — один из рядов постоянен, поэтому корреляция не определена.
- \`ambiguous\` — несколько сдвигов дают одинаковый по модулю коэффициент в пределах 1e-9; нельзя утверждать, что один лаг уникально лучший.

Значения NULL, пустые, нечисловые, NaN и бесконечности исключаются **попарно**; пропущенные периоды не заменяются нулём. Модуль возвращает результат для каждого сдвига и лучший по модулю коэффициент (при равенстве предпочитает меньший абсолютный лаг).

Корреляция даже с лагом **не доказывает причинность**. Поиск лучшего лага на нескольких сдвигах является разведочным анализом, а не проверкой статистической значимости или автоматическим доказательством опережающего влияния.

## Тестирование и интеграция

\`\`\`bash
python -m unittest backend.llm.test_lagged_series
python -m unittest discover -s backend -p 'test_*.py' -t .
\`\`\`

Тесты покрывают лаги обоих направлений, календарные пропуски, отсутствие данных, постоянные ряды, неоднозначные максимумы, даты, некорректные значения и параметры.

**До закрытия #118 необходимо** реализовать передачу в модуль двух предварительно согласованных рядов из аналитического запроса, добавить структурированный ответ FastAPI и проверить сценарий через реальный frontend (\`VITE_MOCK=0\`). Текущий участок \`backend/llm/ask.py\`, выбирающий первые два столбца ответа без выравнивания по календарю, не следует считать корректной реализацией анализа лагов.
