# LLM-модуль

Подключение к модели через OpenAI-совместимый API и сценарии агента.

| Файл | Что делает |
|---|---|
| `client.py` | Отправляет сообщения модели, получает текст. Настройки — из `.env` |
| `catalog_summary.py` | Сжимает каталог данных (`db/catalog_db.py`) в короткую сводку для модели |
| `describe.py` | Сценарий 1 (#3): описание неизвестных данных простым языком |
| `ask.py` | Сценарий 2 (#4): вопрос → выбор таблицы → SQL → проверка → выполнение → ответ |
| `sql_guard.py` | Проверка SQL модели: только один SELECT из `t`, без опасных функций и чужих таблиц |
| `sql_runner.py` | Таблица `t` с приведёнными типами (по каталогу) и выполнение в read-only транзакции |
| `semantics.py` | Разбор вопроса и смысловая проверка SQL: «сколько» → COUNT/SUM, «разных» → DISTINCT, LIMIT только для топа, фильтры только из вопроса |
| `eval.py`, `eval_cases.py` | Тесты аналитической точности: 53 вопроса с эталоном (SQL или число), уточнения, отказы, диалоги; прямой и сквозной (через FastAPI) режимы |
| `eval_holdout.py` | 15 «незнакомых» вопросов, которые не использовались при настройке агента (BI-06 / #34) |
| `test_ask.py`, `test_semantics.py`, `test_eval.py` | Тесты без модели и без БД |
| `test_describe.py` | Тесты без модели и без БД |
| `Modelfile` | Локальная модель с большим контекстом: `ollama create qwen-bi -f backend/llm/Modelfile` |

## Запуск (из корня проекта)

```bash
pip install -r backend/requirements.txt
ollama create qwen-bi -f backend/llm/Modelfile   # один раз
# В .env: LLM_BASE_URL=http://localhost:11434/v1 и LLM_MODEL=qwen-bi

python -m backend.llm.client                       # модель отвечает?
python -m backend.llm.describe --dry-run           # что уйдёт в промпт
python -m backend.llm.describe \
  --catalog data/schema-catalog.json \
  --relationships data/relationship-catalog.json   # описание данных
python -m backend.llm.ask "Какой канал продаж приносит больше всего выручки?"
python -m unittest discover -s backend -p 'test_*.py' -t .
```

Принцип: факты (строки, типы, пропуски) считает код, модель только
пересказывает их. Так слабая модель (до 80B на проверке, 3B при разработке)
не выдумывает цифры.

## Сценарий 2: как устроено

Модель пишет SQL не к сырой таблице (там всё TEXT, десятичные запятые),
а к подготовленной таблице `t`:

```sql
WITH t AS (SELECT <безопасные приведения по каталогу> FROM raw."таблица")
SELECT * FROM (<запрос модели>) AS q LIMIT 201
```

Числа и даты в `t` уже нужного типа, коды и категории остаются текстом.
Для категорий модели показываются реальные значения (для верных `WHERE`).
Ошибку проверки или базы модель получает обратно и исправляет запрос (до 3 попыток).

Для backend:

```python
from backend.llm.ask import answer_question
from backend.llm.sql_runner import PostgresRunner

runner = PostgresRunner(conn)          # conn — psycopg-соединение под bi_reader
result = answer_question(message, catalog, runner)   # dict по docs/api-contract.md
```

## Точность, уточнения и контекст

- **Выбор таблицы** — кодом: слова вопроса сравниваются с названиями таблиц, колонок
  и значениями категорий («возвраты» → «Продажи», где `Тип операции = 'Возврат'`).
  Ничья — уточняющий вопрос с вариантами; ничего общего — вежливый отказ.
- **Единица счёта**: «Сколько продаж без карты?» — строки или уникальные заказы? —
  уточнение кнопками. «Сколько строк …» / «уникальных заказов …» — считается сразу.
- **Смысловая проверка SQL** (`semantics.py`) до выполнения; проблемы возвращаются
  модели на исправление. Если за 3 попытки надёжного SQL нет — цифры не показываем.
- **Изменение данных** («удали», «обнови») — отказ: доступ только на чтение.
- **Контекст диалога** по `session_id`: ответ на уточнение продолжает исходный вопрос;
  «а теперь только за сентябрь» изменяет предыдущий SQL, сохраняя метрику и группировку.

```bash
python -m backend.llm.ask                     # режим диалога в терминале
python -m backend.llm.eval --gold-only        # проверить эталоны (без модели)
python -m backend.llm.eval                    # полный прогон, отчёт: data/eval-report.json
python -m backend.llm.eval --only ctrl_rows_no_card
```

### Сквозной прогон через API и незнакомые вопросы (BI-06 / #34)

Те же вопросы можно задать запущенному бэкенду — ровно так, как их задаёт фронтенд
(`POST /api/chat/jobs` + опрос `GET /api/chat/jobs/{id}`). Проверяется вся цепочка
FastAPI → агент → PostgreSQL → ответ; числа берутся из таблицы ответа, которую видит
пользователь. Эталоны по-прежнему считает PostgreSQL напрямую.

```bash
uvicorn backend.app.main:app --port 8000                      # в отдельном терминале
python -m backend.llm.eval --api http://localhost:8000          # 53 вопроса, отчёт: data/eval-report-api.json
python -m backend.llm.eval --api http://localhost:8000 --holdout   # 15 незнакомых вопросов
python -m backend.llm.eval --api http://localhost:8000 --api-sync  # через POST /api/chat
python -m backend.llm.eval --holdout --gold-only                # проверить эталоны незнакомых
```

Отказ засчитывается только при явном `status: "refused"` в ответе (ответ без таблицы —
не отказ); таблица-источник берётся из поля `table_name` ответа, без него кейс с данными —
провал.

Правило для `eval_holdout.py`: если незнакомый вопрос провалился, агента чинят в общем виде,
а сам вопрос под агента не переписывают. Отчёты в `data/` не коммитим.

Выгрузка значений категорий (для теста выбора таблицы без БД, `test_eval.TableChoiceTests`):

```bash
python -c "import json; from backend.llm.sql_runner import PostgresRunner as R; r=R.from_env(); c=json.load(open('data/schema-catalog.json')); json.dump({t['name']: r.category_values(t) for t in c['tables']}, open('data/category-values.json','w'), ensure_ascii=False, indent=1)"
```

## Вид графика по команде в чате (#16)

- «Покажи то же самое кругом / линией / столбцами / таблицей» — без модели: агент
  повторяет последний SQL сессии и отдаёт тот же результат нужным видом.
  Фронтенд обрабатывает такие команды и сам, локально (`frontend/src/lib/chartViews.js`).
- «А теперь по месяцам линией», «Топ-5 городов кругом» — новые условия + вид: фронтенд
  отправляет такой запрос на бэкенд, агент меняет прошлый SQL и строит график нужного вида.
- Круговая диаграмма — только для одной величины и не более 12 частей; иначе агент
  объясняет и показывает столбцами (или линией для времени).
- Без просьбы: время — линия; «доля / структура / распределение» при ≤ 8 частях — круг;
  иначе столбцы.

## Сравнение периодов и сегментов — Smart Compare (#29)

- Периоды разбирает код (`compare.py`): «август и сентябрь 2025», «сентябрь 2025 с предыдущим
  месяцем», «2025 год по сравнению с 2024», «1 квартал 2025 и 1 квартал 2026». Месяц без года —
  последний такой месяц в данных; год, указанный один раз в конце, относится ко всем месяцам.
- Модели даются точные границы дат: она пишет один запрос с колонкой на период через
  `FILTER (WHERE …)`; проверка требует оба периода и запрещает фильтр по дате в WHERE.
- Изменение («Изменение», «Изменение, %») и вывод считает код: итог, лидер роста и падения.
  График — столбцы, серия на каждый период.
- «Сравни Москву и Казань» — обычный запрос с двумя группами; разницу и процент считает код.
- В диалоге: «…за сентябрь 2025» → «Сравни с предыдущим месяцем».

## «Что если» (#56) и прогноз (сценарий 10)

- «Что будет с выручкой по каналам, если скидка вырастет на 5 п.п.?» — агент обычным путём
  считает **базу**, затем код (`whatif.py`) подставляет изменение в формулу показателя
  (`"Скидка, %" + 5`, `"Цена…" * 1.1`) и пересчитывает в PostgreSQL. Результат: «Сейчас»,
  «При сценарии», изменение и %. Изменения: «на N%», «на N п.п.», «вдвое», «в N раза».
- Если изменяемой величины нет в формуле («если средний чек вырастет на 10%») — пропорциональный
  расчёт с явным допущением.
- «Прогноз выручки на следующий квартал / год / 6 месяцев» — помесячный ряд + линейный тренд
  (`advanced_analytics.linear_extrapolation`); график «Факт» и «Прогноз».
- «А если скидка вырастет на 5 п.п.?» после вопроса о выручке — сценарий к прошлому вопросу.
- Кэши значений категорий и диапазонов дат разделены по источникам (сервер:порт/база).
